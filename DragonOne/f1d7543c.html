微信小程序虚拟支付实战：从下单签名到发货回调的完整闭环

微信官方从2026年开始支持个人用户虚拟支付（Virtual Payment）。 本文记录完整的对接方案，文中代码均为脱敏改写后的示例，仅用于说明方案。

一、整体架构

关键点：

  1. 前端拿到的四元组（signData / paySig / signature / mode）直接透传给 wx.requestVirtualPayment。
  2. 发货以微信消息推送为准，前端 success 回调只刷新 UI，不做发货。
  3. 定时任务兜底查单，防止消息推送丢失导致用户付了钱没到账。

三、下单

3.1 核心流程

前端选完充值金额后，调用下单接口，后端做四件事：

  1. 校验用户状态与道具有效性；
  2. 生成商户订单号 outTradeNo，落库一条「待支付」订单；
  3. 按官方格式拼 signData；
  4. 计算 paySig 和 signature 两个签名，连同 mode 一起返回。

3.2 双签名算法

微信官方文档：签名算法

微信虚拟支付要求两个签名，算法都是 HMAC-SHA256 转十六进制，但密钥和内容不同：

坑点总结：

  • 参与签名的 postBody 必须与实际发给微信的请求体逐字节一致。Java 里千万别用文本块 """...""" 拼
    JSON——文本块会自动加末尾换行并做缩进剥离，字节变了签名就对不上，微信会返回 90010 签名错误。正确姿势：用 JSON
    序列化生成一次字符串存到变量里，签名和发送复用同一个变量。
  • paySig 的密钥是 AppKey，signature 的密钥是用户 session_key，两者别搞混。
  • 沙箱和现网的 AppKey 不同，env 传错签名必然失败。

五、发货回调：消息推送（安全模式）

回调接口需要有两个同名不同请求方式的接口：比如 /api/wechat/notify(GET)和/api/wechat/notify(POST)
,GET接口主要是在后台配置保存时，微信方进行确认的，只有确认后才能进行保存；而POST接口就是实际用户支付后的回调接口。

5.1 协议

在 MP 后台「开发 → 开发管理 → 消息推送配置」开启安全模式（数据格式选 JSON），微信会向配置的 URL 推送事件：

  • GET：首次配置时的 URL 验证，signature = sha1(sort(token, timestamp, nonce))，验签通过原样返回 echostr。
  • POST：正式推送。先验 msg_signature = sha1(sort(token, timestamp, nonce, Encrypt))，再用 EncodingAESKey 做 *
    AES-256-CBC* 解密 Encrypt 字段，明文结构为 16B 随机 + 4B 大端 msg_len + msg(JSON) + appid。

5.2 关键实现

微信官方文档：接收消息推送

官方提供了明文模式和安全模式两种解密方式，明文模式就是简单的接口对接，这里主要说安全模式。

验签/解密直接复用微信官方示例 WXBizMsgCrypt，不要自己造轮子。
